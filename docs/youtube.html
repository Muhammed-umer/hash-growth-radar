YouTube, exactly

What we got from Google, what it allows, what we send, what comes back, what we keep, and what the AI does with it. Every parameter below is taken from Google's reference pages and from the code as deployed on 16 Sep 2026.

Superseded on 17 September 2026. Sections 3, 7, 8 and 9 describe the first version (4 topics per run, the top 5 videos by relevance, the newest 50 comments). That version was replaced by the watch list: every video is remembered, found through a month sweep, newest-first searches and channel upload lists, and comments are read only from videos whose comment count changed. The current design, its jobs and its budget are in coverage-plan.html. What still holds: Google's quota facts at the top of section 2, and section 6 (the AI form and how the score is built; the score's age penalty is now recalculated every hour). Section 7's six phrases are unchanged, but they are no longer searched one call per run. Sections 1, 2 (the spend table), 3, 4, 5, 8, 9 and 10 describe the first version and are kept as history, each marked "first version". Today the tool uses five kinds of request (search, videos, channels, playlist items, comment threads), reads replies and many pages per video, keeps comments from 1 January 2026, and deletes stored comments 30 days after YouTube last returned them.

1 · The API we have (first version)

YouTube Data API v3, Google's official interface to public YouTube data. We use it with an API key created in the Google Cloud console under a project named Hash Growth Radar, restricted to this one API. An API key allows reading public data only. Anything that acts as a user (posting a comment, liking, subscribing, reading private data) needs a different kind of login that we do not have and do not want.

What the API can read with a key

  • Search videos, channels and playlists by phrase (search.list). We use this.
  • Comment threads under a video (commentThreads.list). We use this.
  • Details of specific videos: views, likes, comment count, duration, category (videos.list). Not used.
  • Channel details, playlists, captions, categories, regions. Not used.

The tool makes exactly two kinds of request to Google. Nothing is ever written to YouTube.

2 · The allowance, and what we spend

Google's words: "Projects that enable the YouTube Data API have a default quota allocation of 100 search.list calls, 100 videos.insert calls, and 10,000 units per day combined for all other endpoints." And: "Daily quotas reset at midnight Pacific Time (PT)." That is 12:30 PM or 1:30 PM in India depending on the season.

100 searchesper day. One search.list call = 1 search, its own bucket
10,000 unitsper day for everything else. One commentThreads.list call = 1 unit
Free allowanceOver the limit, calls are refused with "quotaExceeded" until the reset
More on requestThrough the "YouTube API Services - Audit and Quota Extension Form", after a compliance audit

Also from Google: "All API requests, including invalid requests, incur at least a one-point quota cost." So a broken call still costs.

3 · Finding videos: search.list (first version)

One call per topic. This is the request the tool sends, then the full list of what Google accepts and which ones we actually pass.

GET https://www.googleapis.com/youtube/v3/search
    ?part=snippet
    &q=PCOS diet plan
    &type=video
    &order=relevance
    &publishedAfter=2026-06-18T00:00:00.000Z
    &maxResults=5
    &relevanceLanguage=en
    &key=…

What comes back, and what we keep

For each video: the video id, title, description, channel id, channel title, publish date, thumbnails. We keep three things: the video id (to read its comments next), the title (shown on the card as "Under the video: …"), and the channel title (shown as the community, for example YouTube · Sonia Narang).

YouTube returns results in the requested order. It does not return a score or rank number for a video. View and like counts would need a separate videos.list call (1 unit per 50 videos), which the tool does not make today.

Source: developers.google.com/youtube/v3/docs/search/list, read 16 Sep 2026. Code: src/lib/collectors/youtube.ts.

4 · Reading comments: commentThreads.list (first version)

One call per video found in step 3. A "comment thread" is a top-level comment plus its replies; we read the top-level comment only.

GET https://www.googleapis.com/youtube/v3/commentThreads
    ?part=snippet
    &videoId=…
    &order=time
    &textFormat=plainText
    &maxResults=50
    &key=…

Every input Google accepts, and what we pass

ParameterMeaningWe passOur value and why
partRequired. id, snippet, replies.yessnippet: the top-level comment's text and details. Replies are not fetched.
videoIdExactly one of these three filters must be given: videoId (threads on one video), id (specific threads), allThreadsRelatedToChannelId (all threads on a channel).yesThe video id from step 3.
orderTwo values only: time (default, newest first) and relevance (what YouTube shows as "Top comments").yestime. Newest first, so comments posted since the last run are always at the top.
textFormathtml (default) or plainText.yesplainText, so the text needs no cleaning before the AI reads it.
maxResults1 to 100. Default 20.yes50 (youtube_comments_per_video in the code). Still 1 unit whatever the number.
keyThe API key.yesSame key.
searchTermsOnly comments containing these words.noNot used. It would let YouTube pre-filter for words like "metformin"; we filter ourselves after fetching. Possible improvement, untested.
moderationStatuspublished (default), heldForReview, likelySpam. The last two need the channel owner's login.noDefault: published comments only.
pageTokenNext page of comments.noFirst page only (50 newest).

If a video has comments switched off, Google answers "commentsDisabled"; the tool counts it and moves on. A single failing video never stops the run.

5 · How a comment is stored (first version)

Each kept comment becomes one row in the items table of the Supabase database. Before the row is written, three checks run in this order:

  1. Posted within the last 7 days? If not, it was stored with status filtered and reason too_old, and never sent to the AI. (Today the rule is "posted before 1 January 2026".)
  2. Seen before? The table has a uniqueness rule on (platform, external id). The external id is the YouTube comment id, so a comment fetched in an earlier run is silently ignored. Nothing is counted or tagged twice.
  3. Keyword filter. Plain code, no AI: the text must be at least 15 characters, must contain at least one word from the allow list (medicines like metformin, conditions like PCOS, tracking words like calorie or diet app, phrases like what to eat), must contain no word from the block list (giveaway, crypto, hiring, meme …), and must look like a question (a ? or a phrase like "can I", "should I", "which app"). Whole words only, so rice does not match price.

The row

There is no username column in this table or any other. A daily job deletes every row 7 days after collected_at. Google's own rule for API data is 30 days at most; ours is stricter.

6 · Why the AI, and what it does

The keyword filter cannot understand a sentence. "Is roti okay with my sugar tablets?" contains no medicine name and no condition name, yet it is a perfect match. "Metformin is the worst, switched to keto, feeling great" contains a medicine name and is useless. Telling those apart needs reading, and that is the one job the AI has.

For each queued item, one request goes to Google's Gemini (model gemini-3.5-flash-lite by default, or whatever GEMINI_MODEL names; free tier; several keys rotated so the per-minute limit is rarely hit). The request contains fixed instructions, the comment text (platform, channel, text; no username, no link), and a strict schema for the answer. The model must return this form and nothing else:

FieldWhat the AI fills in
intentOne of five groups, below.
conditionsHealth conditions named in the text itself, e.g. ["type 2 diabetes"]. Never guessed.
medicinesMedicines named in the text itself, e.g. ["metformin"]. Never guessed.
competitorA competitor app named in the text, or nothing.
fit_score0 to 100: how directly a medicine- and condition-aware food tracker answers this exact text.
urgencylow, medium, high.
languageen, hinglish, other.
do_not_reply + reasontrue when this is not someone to approach: asks for a dosage or a diagnosis, describes an emergency, or is about eating disorders, self-harm or mental health.
summaryOne plain sentence saying what is asked, with no name in it.

The five groups

intentMeaningExampleBecomes
medicine_food_questionAsks what to eat, avoid, or time around a medicine or a named condition"Can I keep eating rice on metformin?"to look at, +15
app_recommendationAsks for or compares calorie, diet or food-logging apps"Which app understands Indian food?"to look at, +10
competitor_complaintComplains about a specific competitor app"Cal AI keeps calling my dal pasta"to look at, +5
nutrition_questionGeneral diet question, no medicine or condition"Is oats good for weight loss?"to look at, +0
irrelevantPraise, jokes, spam, no question"Great video sir"dropped

After the answer comes back, plain code takes over again: the answer is checked against the schema (an out-of-range score or an unknown group is rejected and asked once more); the row in tags is written; do_not_reply makes the item not suitable, irrelevant makes it filtered, anything else makes it tagged (on the list) with score = fit score + the group bonus above + urgency (0, 3 or 6) − 2 per full day since the comment was posted, capped at −14. The age part is recalculated every hour. The Today page shows the top 10, by score (the default) or newest first.

Code: src/lib/ai/prompts.ts, src/lib/types.ts, src/lib/pipeline/score.ts, src/lib/pipeline/run.ts.

8 · Why 4 topics per run, and which 4 (first version)

The timer runs 12 times a day. Searching all 6 topics every run would be 72 searches, most of the 100 allowed. So each run searches 4, and consecutive runs continue through the list.

The rule

  1. Count 2-hour blocks since 1 January 1970 (the zero point every computer clock uses). This "window number" goes up by one every 2 hours.
  2. Multiply by 4 (topics per run).
  3. Divide by 6 (number of topics) and keep the remainder. That is the position in the list where this run starts.
  4. Take 4 topics from there, wrapping to the top of the list at the end.

9 · The same 5 videos and the same 50 comments, again (first version)

Within 4 hours the top 5 videos for a topic rarely change. So most runs return the same 5 videos, and most of their 50 newest comments were already seen. This is expected. What we want from a video is not the video, it is the comments that arrived since we last looked, and a popular diet video keeps receiving question comments for weeks.

How the repeats are handled

  • Same video again: costs 1 unit. Reading it again is the point.
  • Same comment again: rejected by the uniqueness rule on the comment id (section 5, step 2). It is not stored, not filtered, not sent to the AI. Only comments new since the last look go through.
  • Where you see it: every run record on the YouTube page shows "fetched" and "new". The first run showed fetched 117, new 117. A later run of the same topics shows a similar "fetched" and a small "new".

The 50-comment window

  • Quiet video (fewer than 50 new comments since the last look, which is almost every video): the newest 50 contain all the new ones plus some known ones. Known ones are dropped, new ones pass. Nothing is missed.
  • Busy video (more than 50 new comments in about 4 hours): comments beyond the 50th newest are not seen. This is the one real gap. youtube_comments_per_video can be raised to 100 in the code at no extra cost (still 1 unit per video).
  • Why not "comments since time X"? The comment endpoint has no such filter (section 4 lists every parameter it has). Newest-first plus the id check is the only way, and it needs no memory.

A brand-new video appears only once YouTube ranks it in the top 5 for the phrase. Switching order to date would show new uploads immediately at the cost of more low-quality videos. Not done; it is one word in the code.
